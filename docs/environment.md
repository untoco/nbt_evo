# Окружение и инструменты

Версия: 2026-11-18. Инструкция описывает существующие команды; результаты их проверок приведены в [фактах](facts.md).

## Загрузка ресурсов и развёртывание через Ansible

На подготовленном Mac Apple Silicon нужны работающий Docker, Ansible, Python 3.11+, Git и curl. Из корня репозитория выполняются две команды:

```sh
./tools/nbt-env fetch
./tools/nbt-env setup
```

**fetch** работает напрямую в терминале. Для архивов curl показывает объём, процент, скорость и ETA; Git, Docker, APT и npm выводят собственный прогресс. Оценка времени доступна, когда сервер сообщает размер файла. Повторный запуск использует проверенный кэш и продолжает `.part`. Одновременный запуск двух fetch блокируется; wget и другие загрузчики нужно завершить перед fetch.

Загрузчик подготавливает:

- Базовые Docker-образы для нужной архитектуры.
- Закреплённую ревизию QNX-комплекта, Debian-пакеты, подписанные индексы и GNU-исходники.
- Архивы Ghidra, Node и REA.
- APT-пакеты для dev и REA, Python wheels и npm-кэш со всеми разрешёнными зависимостями REA.

Python wheels для CPython 3.10 Linux AMD64 загружаются на хосте через curl: URL, размер и SHA-256 закреплены в [манифесте](../tools/nbt-dev/python-wheels.lock.json). При обрыве сохраняется `.part`; сборка дополнительно проверяет хеши через pip `--require-hashes` без сети. Для загрузки APT и npm запускаются временные контейнеры базовых образов. Пакеты в macOS не устанавливаются. Компоненты можно выбрать явно: `./tools/nbt-env fetch --components qnx re`. По умолчанию подготавливаются dev, qnx и re; выбор должен покрывать компоненты локального Ansible-конфига.

При подготовке Debian-пакетов QNX сначала проверяются кэш и точные имена файлов. Остальные `.deb` рассматриваются только для недостающих пакетов; кандидаты с флагом macOS `SF_DATALESS` пропускаются без чтения и удаления. В итоговый перечень QNX входят только пакеты из манифеста, закреплённые GNU-архивы и используемые файлы индексов; посторонние файлы в этих каталогах не хешируются.

Для QNX список исходных файлов и отдельный контекст `.build/nbt-qnx/generated/context` формируются из файлов C/C++-комплекта, учтённых во вложенном Git-репозитории `tools/qnx`. Неучтённые файлы не читаются и не удаляются. Обязательный файл с флагом `SF_DATALESS` вызывает явную ошибку с предложением восстановить его локально. Новый контекст сначала полностью копируется в соседний `context.staging-*`, затем заменяет рабочий каталог. Предыдущий контекст сохраняется в `context.previous-*`; ошибка копирования оставляет рабочий каталог на месте, а ошибка замены запускает его восстановление. Сохраненные каталоги не удаляются автоматически и занимают дополнительное место; их пути выводятся при подготовке.

Служебные файлы macOS `.DS_Store` и AppleDouble (`._*`) исключаются из перечня зависимостей и его проверки; реальные файлы APT, wheels и npm по-прежнему проверяются по SHA-256.

После успешной загрузки создаётся `.build/downloads/ready.json`: перечень файлов с SHA-256 и отпечатки рецептов. Подписанные индексы APT дополнительно проверяются APT в базовых контейнерах. Источники и контрольные файлы QNX заданы в [lock-файле](../tools/nbt-dev/toolchain.lock.json), архивы REA — в [манифесте](../tools/nbt-re/artifacts.lock.json).

**setup** запускает [playbook](../automation/ansible/environment.yml), который:

1. Проверяет инструменты и Docker, создаёт рабочие каталоги и локальный конфиг из [шаблона](../config/nbt/environment.example.yml).
2. Проверяет готовность выбранных ресурсов, их хеши, рецепты и базовые образы. Если чего-то не хватает, останавливается с предложением выполнить fetch.
3. Собирает недостающие образы, подключая локальные пакеты, wheels и npm-кэш. RUN-этапы сборки выполняются с `--network none`, APT использует `--no-download`, pip — `--no-index`, npm — `--offline`.
4. Проверяет инструменты, компиляцию C/C++98, Ghidra и декомпиляцию тестового QNX ELF с проверкой неизменности файла.
5. Создаёт конфиг MCP и сохраняет `.build/bootstrap/result.json`.

Это отделяет загрузку больших ресурсов от Ansible. Docker daemon может обращаться к registry за метаданными FROM; полная изоляция daemon от интернета отдельным испытанием ещё не подтверждена. Исходные пакеты и зависимости внутри RUN не скачиваются.

Контейнеры команд удаляются после завершения. Playbook не меняет настройки Colima и не обращается к автомобилю. Локальные параметры в `config/nbt/environment.local.yml` сохраняются: nbt_components выбирает dev/qnx/re, nbt_rebuild включает пересборку. nbt_offline сохраняет режим проверки заранее готовых образов без сборки. Параметры REA находятся в существующем re.local.json.

Другие команды:

```sh
./tools/nbt-env plan
./tools/nbt-env check
```

plan показывает список задач. check проверяет готовые образы; загрузки и сборки не запускаются. Ansible можно вызвать напрямую: `ansible-playbook -i localhost, automation/ansible/environment.yml`.

Журнал Ansible — `.build/bootstrap/latest.log`. Успех отмечается сообщением `Environment verified` и `failed=0` в PLAY RECAP. После сбоя выполняется повтор соответствующей команды; готовые файлы сохраняются. Первая сборка QNX может занимать десятки минут.

## Где что работает

| Компонент | Место запуска | Назначение |
|---|---|---|
| Python 3.11+, системные SSH и сетевые утилиты | macOS | Конфигурация сеанса, ENET, чтение/копирование через SSH |
| nbt-evo-dev:2026-11-14 | Docker, Linux AMD64 | Общие инструменты сборки и анализа |
| nbt-evo-qnx-armv7:8.5-arm64-2026-11-14 | Docker, Linux ARM64 | GCC 8.5, сборка ARM32 QNX |
| nbt-evo-re:ghidra12.2-rea6.9.0 | Docker, Linux ARM64 | Ghidra/REA; версии и хеши зафиксированы в artifacts.lock.json |

ARM64 здесь описывает платформу компилятора; выходной QNX ELF имеет архитектуру ARM32. Совместимость с C++ ABI BMW HMI этими сборками не проверена.

Нужны уже работающий Docker, Git, Python и curl. При использовании Colima каталог проекта должен быть доступен виртуальной машине. SDK и библиотеки HU в публичный clone не входят. На Mac не требуется устанавливать Java, Node или компилятор QNX для запуска этих контейнеров.

## Bavarian: временный SSH на macOS

[Bavarian SSH Client](https://ssh.bavarian-aa.uk/) — внешний GUI-клиент. Издатель заявляет временное открытие SSH до перезагрузки HU. Работа с клиентом состоит из двух действий владельца на macOS с Python 3.11+ и curl:

```sh
./tools/nbt-bavarian update
./tools/nbt-bavarian open
```

1. **update** — отдельный пользовательский этап получения клиента. Проверяет доступность официального `SHA256SUMS`, извлекает актуальный SHA-256 macOS ZIP, проверяет локальный архив и при необходимости скачивает его с прогрессом/resume. Затем подготавливает `.app`: проверяет ZIP-пути, подпись `codesign --verify --deep --strict`, архитектуру через lipo и записывает фактическую bundle version, хеши и права файлов. Уже проверенная актуальная `.app` повторно не распаковывается. Измененная или неполная копия сохраняется как `prepared.previous-*` и готовится заново из проверенного архива.
2. **open** — проверяет выбранные локальный архив и `.app`, затем открывает GUI. Не проверяет сайт, не скачивает обновления и не нажимает кнопки клиента. После открытия клиент может выполнять собственный сетевой обмен.

Файлы находятся в `.build/bavarian/<archive-sha256>/`. SHA-256 выбранного выпуска и дата проверки фиксируются в `.build/bavarian/current.json` **после успешной подготовки**. Обновление не редактирует Git lock-файл: [bavarian.lock.json](../tools/bavarian.lock.json) задает URL/имена и первоначальную закрепленную версию, локальная запись фиксирует выпуск, выбранный update. Имена файлов и URL не берутся из checksum index или локальной записи. Старые версии сохраняются. При ошибке сети, некорректном индексе, несовпадении SHA-256, отказе подписи/архитектуры новая версия не выбирается; update завершается с ошибкой, не объявляя клиент актуальным. Ранее выбранный исправный выпуск можно открыть отдельно.

Актуальность определяется по содержимому архива (SHA-256), не по строке changelog. `CFBundleShortVersionString`/`CFBundleVersion` выводятся из `.app`; у неизвестного нового SHA версия changelog обозначается `unknown`. На 2026-11-18 опубликованный macOS SHA совпал с начальным lock-файлом; реальный ZIP в этой проверке не загружался.

Приложение не устанавливается в Applications; Gatekeeper и проверка подписи не отключаются. Перед строгой проверкой подписи из управляемой `.app` удаляются только `com.apple.FinderInfo` и `com.apple.ResourceFork`, мешающие codesign. Это выполняется также при check/open: метаданные могут появиться после распаковки. Quarantine, provenance, атрибуты File Provider, содержимое файлов и исходная подпись сохраняются; приложение не переподписывается. Проверка codesign подтверждает целостность подписи, а не наличие Developer ID или нотариализации издателя.

В GUI для **временного SSH** используйте **Enable SSH**. **Install/Pair** управляют NBTApps agent и не нужны для этого действия. Диагностический gateway и SSH endpoint HU — разные адресаты; `SSH enabled` нужно подтвердить подключением. При нескольких интерфейсах проверяйте маршрут к машине и отдельный доступ клиента в интернет.

`./tools/nbt-bavarian check` оставлен для дополнительной офлайн-проверки без запуска. Прежние `tools/nbt-env fetch --components bavarian` и `tools/nbt-bavarian prepare` сохранены как раздельные низкоуровневые этапы для уже выбранного выпуска; они не проверяют его актуальность на сайте. Docker/Ansible клиенту не нужны, в `nbt_components` Ansible его добавлять не надо. Playbook и open не выполняют update автоматически; inventory dev/qnx/re не перезаписывается.

Изолированные тесты используют синтетические архивы и подмененные команды. Они проверяют обновление, повторное использование, восстановление измененной копии и сохранение прежнего выбора при сбое. Работа реального приложения и SSH на HU ожидают проверки владельцем. Приложение не распространяется через этот репозиторий; действуют условия издателя, включая запрет продажи и включения в платные комплекты.

## Ghidra и REA

Из корня проекта:

```sh
python3 tools/nbt_re.py init
./tools/nbt-env fetch --components re
python3 tools/nbt_re.py build
python3 tools/nbt_re.py doctor
```

init создаёт локальный `config/nbt/re.local.json` из [примера](../config/nbt/re.example.json). fetch подготавливает архивы, APT-пакеты и npm-кэш; build собирает образ по [Dockerfile](../tools/nbt-re/Dockerfile) с отключённой сетью RUN-этапов. Анализ в подготовленном образе запускается с `--network none --pull never`.

Загрузчик сохраняет `.part` и продолжает его после обрыва. По умолчанию одна попытка ограничена четырьмя часами, выполняется до пяти попыток; отсутствие передачи данных в течение 90 секунд вызывает повтор. Настройки `download_timeout_seconds`, `download_attempts` и `download_stall_seconds` задаются в `re.local.json`. В старых конфигах без этих полей используются новые значения по умолчанию. Полностью докачанный другим клиентом файл `.part` принимается после проверки закреплённого хеша. Ошибка HTTP/таймаут не считается доказательством несовпадения хеша. Не запускать несколько загрузчиков на один файл одновременно.

Пример для имеющегося тестового ELF в локальном каталоге:

```sh
python3 tools/nbt_re.py analyze .build/nbt-re/inputs/fixture-qnx-arm32
python3 tools/nbt_re.py decompile .build/nbt-re/inputs/fixture-qnx-arm32 hu_scale_rpm
python3 tools/nbt_re.py mcp-config
```

ELF отсутствует в Git; его исходник — [fixture.c](../tools/nbt-re/fixture.c). Вместо этого пути можно передать собственный существующий бинарный файл. Анализируемый файл подключается только для чтения. Отчёты и состояние сохраняются в `.build/nbt-re/`; mcp-config создаёт `.build/nbt-re/mcp.json`, не меняя настройки клиента автоматически.

## QNX и общая среда

```sh
./tools/nbt-env fetch --components dev qnx
tools/nbt-dev/run build
tools/nbt-dev/run doctor
tools/nbt-dev/qnx-run check
```

run build собирает общую среду из [Dockerfile](../tools/nbt-dev/Dockerfile). Её doctor отдельно сообщает об отсутствии неподключённых SDK и frameworks.

qnx-run check использует уже подготовленный QNX-образ, компилирует [C](../tools/nbt-dev/examples/hello-qnx.c) и [C++98](../tools/nbt-dev/examples/hello-qnx.cpp) и проверяет ELF. Ожидаемый итог — ELF32 ARM, interpreter `/usr/lib/ldqnx.so.2`, отчёты и SHA-256 в `.build/nbt-qnx/out/`. Команда не запускает программы на автомобиле.

Для пересборки QNX-образа нужны локальные `tools/qnx/`, исходные GNU-архивы и Debian-пакеты. Проверка и сборка:

```sh
python3 tools/nbt-dev/qnx-deps.py check
tools/nbt-dev/qnx-run build
```

[Манифест зависимостей](../tools/nbt-dev/dependencies-arm64.json) и [подготовка сборки](../tools/nbt-dev/prepare-qnx-build.py) находятся в Git; сами локальные пакеты, SDK и лицензии исключены. Подготовленный анализ и компиляция примеров работают без сети. fetch загружает закреплённый публичный QNX-комплект и зависимости; установка оригинального лицензируемого QNX SDP и получение библиотек HU в playbook не входят.

## Сетевые инструменты и журналы

```sh
python3 tools/enet_identify.py --help
python3 tools/nbt_session.py init
python3 tools/nbt_session.py --dry-run collect
python3 tools/nbt_hsfz_trace.py --help
```

[enet_identify.py](../tools/enet_identify.py) реализует discovery и диагностическое чтение. [nbt_session.py](../tools/nbt_session.py) использует локальный конфиг из [шаблона](../config/nbt/session.example.json). dry-run показывает действия без подключения. Сбор файлов через SSH целиком на нашей HU ещё не проверен из-за отсутствия успешного входа.

[nbt_hsfz_trace.py](../tools/nbt_hsfz_trace.py) обрабатывает локальный PCAP и выдаёт метаданные без challenge, подписей, VIN и содержимого служебных параметров. [nbt_ssh_relay_probe.py](../tools/nbt_ssh_relay_probe.py) содержит ограниченный relay-клиент; unit-тесты не означают успешного открытия SSH на HU.

## Проверка перед публикацией

```sh
python3 -m unittest discover -s tools/tests -v
python3 tools/check_public.py
git diff --cached --check
```

check_public проверяет отслеживаемые файлы, в том числе блокирует принудительно добавленный research/. Содержательную проверку фактов автоматический сканер не заменяет.
