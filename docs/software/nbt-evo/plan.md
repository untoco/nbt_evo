[Раздел ПО автомобиля](../README.md)

**Цель — запустить своё приложение на магнитоле, затем показать в нём параметры машины.**

## Что делаем дальше

1. **Узнаём версию магнитолы.** На стоящей машине подключаем Mac по ENET, сохраняем результат нашего скрипта и фото версии NBTevo из меню.
2. **Получаем файлы машины через SSH.** Сохраняем ОС/архитектуру, разрешение экрана и две библиотеки HMI с SHA-256. Способ открытия SSH выбираем по фактической firmware.
3. **Запускаем консольный Hello World.** Сначала сверяем целевую ОС, архитектуру и зависимости. Затем проверяем вывод, завершение и повторный запуск.
4. **Делаем своё приложение для экрана.** По файлам HU проверяем совместимость C++ ABI и компилятора. Первый интерфейс — текст и счётчик; затем проверяем локальный CDS API и подписку на один параметр, например RPM. Образец API найден в EntryNav2, совместимость с QNX ещё не подтверждена. Приборку и открытие по DSC OFF добавляем позже.

Начато выполнение шага №1: ENET discovery и TCP 6801 проверены на машине, шлюз **169.254.97.91**, VIN совпал. Идентификаторы HU/KOMBI прочитаны, владелец сообщил X20511I, IP HU по DID 172A — **169.254.199.99**. **Ближайший шаг — осмотреть Ethernet-разъём и проводку ретрофита на задней стороне HU.** Пассивный захват уже подтвердил положительные ответы на FD2E/FD2F/FDAC официального клиента; ошибка relay 0x84 появляется после них. Feature Installer исключён. Найден первичный отчёт с теми же симптомами и недостающим подключением Quadlock → отдельный Ethernet-разъём. На нашем F21 это гипотеза: установщик другой, проводка неизвестна. Адрес .119 и повторный discovery доступа не дали; Mac подключён к Wi-Fi HU: 172.16.224.117 → 172.16.224.1, ping работает; после повторного Enable SSH TCP 22/23/8000 не отвечает. Интернет по iPhone USB сохранён приоритетом сетевых служб. Локальные сбор/сборка работают офлайн; Bavarian использует внешний сервер. Подключения и активные диагностические/исследовательские запросы разрешены владельцем без обязательного стенда и повторных подтверждений на каждый запрос. Прошивка, кодирование, запись параметров и управление исполнительными механизмами требуют авторизации соответствующих работ и подготовки восстановления.

Уточнение после SupraMKV: опубликованный pf.conf другой HU разрешает CarPlay-порты без явного разрешения SSH, хотя netstat показывает SSH listener на всех адресах. Это объяснение возможной фильтрации Wi-Fi, а не доказанная конфигурация нашей машины. Wi-Fi в исходной инструкции — внешний ENET-адаптер. Проверка Ethernet-проводки остаётся ближайшим шагом; после доступа к оболочке сначала читаем действующие сетевые правила и конфигурацию SSH. [Файлы и границы вывода](knowledge-base.md#supramkv-ssh-guide-и-опубликованная-конфигурация-hu-2026-11-16).

**Текущее подключение — modBMW Wi-Fi ENET:** Mac en0 169.254.1.50, адаптер 169.254.128.7, ZGW **169.254.1.47:6801** (VIN подтверждён). Для Bavarian Car IP сейчас указываем .47, а не прежний .97.91. HU сообщает прежний .199.99; после повторного Enable SSH вход по-прежнему недоступен, ARP incomplete. ENET по Wi-Fi проверен, ближайший шаг с проводкой HU не меняется. [Результаты](knowledge-base.md#реальная-проверка-modbmw-wi-fi-enet-2026-11-16).

Статья David Petric добавлена с [проверкой надёжности](knowledge-base.md#статья-david-petric-перепроверка-2026-11-17): ориентиры поиска проверяем по файлам HU; QNX-сборку сохраняем. Ближайший шаг по Ethernet-проводке не меняется.

Для неизвестных методов HMI/CDS и проверки раскладки BMW C++-объектов предусмотрен [статический анализ в Ghidra](knowledge-base.md#ghidra-для-исследования-и-разработки-нативных-приложений). Он потребуется по конкретному вопросу после получения библиотек HU; сборка Hello World и текущая проверка Ethernet от него не зависят. Headless Docker уже подготовлен и проверен на собственном ARM32 QNX ELF; команды и конфиг описаны в базе знаний. Файлов нашей HU пока нет.

Локальная проверка и первый сбор теперь запускаются через конфиг: [краткая инструкция ниже](#первый-сеанс-конфиг-и-один-запуск).

## Офлайн-проверка Ethernet-проводки после ENTRY_BASIS → NBT Evo

Дата инструкции: 2026-11-16. Статус: `planned`, осмотр ещё не выполнен. Владелец уточнил: раньше стоял ENTRY_BASIS, затем доустановлены NBT Evo, расширенная приборка, MOST и выполнены кодировки (`reported`). Точный тип KOMBI и схема Ethernet пока `unknown`.

**Что хотим установить:** подключён ли Ethernet-вход установленной HU к автомобильному диагностическому Ethernet. Рабочие iDrive, приборка, MOST и диагностическое чтение HU через ZGW не доказывают наличие этого отдельного пути. Сейчас ZGW доступен, а прямой HU-IP не отвечает на ARP. Это основание проверить проводку, а не диагноз её отсутствия.

### Подготовка без интернета

1. Открыть этот раздел на Mac заранее либо сохранить его локальную копию на телефон. Интернет, E-Sys и новые программы для осмотра не нужны.
2. Подготовить телефон с камерой и фонарик; пластиковый инструмент и подходящий инструмент для крепежа — только если уже известна правильная процедура доступа к HU для этой машины.
3. Осмотр проводить на стоящей машине, двигатель заглушить. Разъёмы под питанием не снимать. Выключенное зажигание само по себе не подтверждает обесточивание HU. Если для доступа требуется отключать жгуты или снимать блок, сначала нужна штатная процедура снятия/обесточивания для конкретного F21; при её отсутствии ограничиться доступным обзором или поручить снятие установщику. Эта инструкция не задаёт порядок разборки панели, отключения аккумулятора и обратного подключения.

### Куда искать второй конец Ethernet

По документации BMW для F20 шлюз ZGM встроен в **FEM**, расположенный у передней стойки в ногах пассажира (на леворульной машине — справа). Автомобильный конец диагностической линии HU должен идти к FEM, возможно через штатный жгут/переходник. Наши измерения пока не подтверждают этот участок. Ожидаемый путь: `Mac → modBMW/ENET → OBD → FEM/ZGM → Ethernet → HU`.

ATM отсутствует по прямому уточнению владельца, его линию не ищем. Для FEM найден ориентир по опубликованной таблице BMW: **A173*10B, 12 контактов, натуральный/светлый корпус; Ethernet к HU — гнёзда 1, 2, 3, 7, 8**. Сверяем маркировку, отлитые номера и заполненность гнёзд на фотографиях. Источник — таблица FEM для F30 и совпадающая немецкая таблица; применимость к нашему установленному FEM по номеру/VIN ещё не подтверждена. Назначения TX/RX/ETH_A и соответствия контактам нашей NBT Evo в этих таблицах не раскрыты, готовой схемы перепиновки пока нет. FEM сразу не разбирать, штекеры под питанием не отключать. Прямой сервисный кабель HU–RJ45–Mac — другой вариант подключения, не штатный второй конец автомобильной линии. [Контакты и источники](knowledge-base.md#найденные-контакты-fem-a17310b).

### Что осмотреть и сфотографировать

1. **Маркировка HU:** наклейка целиком, читаемые BMW part number, изготовитель и HW-обозначения. Если недоступна без дальнейшей разборки, отметить это, не вытягивать жгут ради фотографии.
2. **Задняя сторона целиком:** общий снимок всех разъёмов и подключённых штекеров до каких-либо действий. Отдельный Ethernet-разъём в обсуждениях ретрофита называют OABR; это не обычное гнездо RJ45. Точное место определяем по маркировке и фотографии именно нашего блока, не по цвету разъёма другой HU.
3. **Небольшие многоконтактные разъёмы рядом с основным жгутом:** сделать крупные фото с двух ракурсов, чтобы было видно, какие гнёзда пустые и куда вставлены штекеры. Не считать любой пустой порт отсутствующим Ethernet, пока его назначение не идентифицировано.
4. **Quadlock и переходники ретрофита:** сфотографировать большой основной разъём и все доступные переходные жгуты/коробочки между штатной проводкой и HU. Наклейки, надписи и видимые ответвления — крупно. Для первичного осмотра Quadlock не разбирать и контакты не извлекать.
5. **Предполагаемый Ethernet-жгут:** если штекер виден, снять его с проводами на фото, не отсоединяя. Проследить только доступный участок: уходит ли в штатный жгут, переходник или заканчивается свободным концом. Если другой конец скрыт, записать «назначение/конец неизвестны». Число или цвет проводов сами по себе назначение не доказывают.
6. **Оптика MOST:** отдельно отметить оптические линии и переходники, не отключая и не перегибая их. Наличие оптики фиксируем отдельно от Ethernet; оно не заменяет проверяемый путь к HU.

### Как трактовать результат

| Наблюдение | Что можно заключить / следующий шаг |
|---|---|
| Назначение нужного разъёма по фото/номеру HU ещё не определено | Пока только исходные фотографии. Проводку не менять. |
| После идентификации Ethernet-вход HU оказался пустым | Прямое подключение в этот вход отсутствует; уточнить схему требуемого подключения для этой HU/F21. Это ещё не готовая распиновка ремонта. |
| Штекер установлен, но кабель заканчивается свободным концом | Зафиксировать конец/маркировки; сквозной путь пока не подтверждён. |
| Штекер установлен, кабель уходит в жгут/переходник | Подтверждён только видимый участок. Следующий шаг — схема именно установленного ретрофита, а затем проверка непрерывности и Ethernet-link специалистом. |
| При доступе обнаружено повреждение, натяжение или неизвестная коробка | Сфотографировать, дальнейшую разборку/переподключение отложить до идентификации. |

**Граница этой проверки:** не переносить четыре провода из Quadlock по картинке F10/F11, не назначать пины по цвету, не подключать RJ45 или самодельный переходник к неизвестному порту, не измерять сопротивление на подключённой/запитанной электронике. Прозвонка — отдельная работа после подтверждённой схемы и безопасного отключения обоих концов. Прошивка, кодирование и повторный Enable SSH для фотографий не нужны; Bavarian использует интернет и не является офлайн-процедурой.

### Что сохранить после осмотра

В заметке достаточно заполнить: `дата; BMW part number HU; фото задней панели; какие порты пустые; предполагаемый Ethernet-штекер установлен/нет/не определён; куда уходит кабель; видимые переходники/маркировки; что осталось недоступно`. Исходные фото затем добавить в media/ и связать с этим планом; наклейки могут содержать серийные номера, публично их не выкладывать. Работоспособность iDrive/приборки до и после доступа проверить после штатной сборки, а не со снятыми жгутами.

Основание гипотезы — [первичный отчёт о ретрофите F11](https://github.com/Sq00ky/Supra-iDrive6-Android-Auto/issues/139#issuecomment-6748718241) и [фотографии автора](https://github.com/Sq00ky/Supra-iDrive6-Android-Auto/issues/139#issuecomment-6749209993), `reported`, другая машина. Это ориентир для осмотра, не подтверждённая схема F21. После осмотра продолжаем здесь же, не создаём отдельный план.

## Первый сеанс: конфиг и один запуск

`confirmed`: автоматизация проверена локально и на имитаторах. `unknown`: фактическая работа с нашей машиной. Команды выполняются на Mac, установка дополнительных Python-пакетов не требуется.

### 1. Конфиг уже подготовлен

Локальный файл — `config/nbt/session.local.json`. Он исключён из Git, пароля в нём нет. [Пример и все параметры](../../../config/nbt/session.example.json).

Для нового checkout создать его один раз:

```sh
cd /path/to/nbt_evo
python3 tools/nbt_session.py init
```

Повторный `init` существующие настройки не перезаписывает. Обычно нужно заполнить только эти поля:

| Поле | Что указать |
|---|---|
| `network.interface` | Оставить пустым для автовыбора единственного интерфейса `en…` с `169.254.x.x`. Для Wi-Fi/нескольких адаптеров указать `en…` из подсказки сборщика |
| `head_unit.ssh_ip` | Отдельно подтверждённый IPv4 магнитолы. Можно оставить пустым на первом сеансе — сохранятся данные ENET |
| `head_unit.firmware` | Полный код `NBTevo_…` из меню, если известен. Если HU отдаёт код по SSH, он определится автоматически |
| `ssh.legacy` | Обычно `false`; при ошибке согласования старых SSH-алгоритмов переключить в `true` |

`network.local_ip` и `network.broadcast` вычисляются по выбранному интерфейсу. `network.gateway_ip` определяется через discovery, если ответил ровно один шлюз. Эти поля можно закрепить в конфиге фактическими адресами. При неоднозначности сборщик сохраняет результаты и просит указать значение — первый попавшийся адрес не выбирается.

**Диагностический шлюз и SSH-адрес HU — разные параметры.** Сборщик не выдаёт IP шлюза за адрес магнитолы.

В разделе `capture` можно изменить фактические пути двух HMI-библиотек, каталоги поиска runtime и отдельные runtime-пути. Пустые runtime-пути означают поиск. Остальные значения оставить по примеру. Поле `password` не поддерживается: пароль вводится только в запрос OpenSSH.

### 2. Проверить локальную готовность

```sh
python3 tools/nbt_session.py check
```

Команда проверяет конфиг, наличие инструментов, 111 локальных пакетов и сборку примеров C/C++ в имеющемся Docker. К автомобилю не подключается, ничего не скачивает. Ожидаемый итог:

```text
Конфиг и локальные инструменты проверены. Соединений с машиной не было.
```

При желании посмотреть действия без подключения:

```sh
python3 tools/nbt_session.py collect --dry-run
```

Вывод — JSON с параметрами, чтениями и `writes_to_hu: false`. Сетевых подключений и диагностических запросов в этом режиме нет.

### 3. Подключить автомобиль и собрать данные

На стоящей машине включить зажигание, дождаться загрузки iDrive и подключить ENET либо сеть modBM Wi-Fi. Сделать фото версии `NBTevo_…`.

```sh
python3 tools/nbt_session.py collect
```

Дальше автоматически выполняются:

1. Чтение интерфейсов Mac и вычисление локального IP/broadcast.
2. Обнаружение единственного шлюза либо использование его IP из конфига; проверка маршрута и порта 6801.
3. Чтение идентификаторов ZGW/HU/KOMBI через существующий ENET-клиент.
4. Если задан `head_unit.ssh_ip` — проверка маршрута и порта 22, SSH-вход, чтение ОС/firmware/экрана/CPU.
5. Копирование двух HMI-библиотек, поиск и копирование указанных runtime-файлов.
6. Проверка заголовков ARM ELF32, вычисление SHA-256, сохранение отчёта и закрытие общего SSH-соединения.

При первом SSH-входе сверить показанный fingerprint с доверенным источником доступа. Первый диалог и его ошибки OpenSSH показывает прямо в Терминале; этот диалог не записывается в лог, в отчёте сохраняется код завершения. При пароле запускать сбор из обычного Терминала. Соединение переиспользуется для чтений; секреты в конфиг или отчёт не добавляются.

Для `collect` нужны только Python/OpenSSH и системные сетевые команды Mac; Docker запускать не требуется. Интернет у машины не нужен. Discovery и диагностические чтения — **активные запросы**, а не пассивная запись CAN. Адреса/DID остаются кандидатами из ENET-клиента; отрицательные ответы сохраняются без утверждения о поддержке.

### 4. Прочитать итог

Пример формы вывода, не результат на нашей машине:

```text
Сеанс: …/.build/nbt-qnx/sessions/2026-11-15_…/
Результат: complete; файлов HU: …
```

| Итог | Что делать |
|---|---|
| `complete`, код 0 | Запрошенный сбор завершён. Это ещё не совместимость с нашей программой |
| `partial`, код 2 | Собранное сохранено. Прочитать подсказку и `summary.json`: например, дописать `head_unit.ssh_ip`, проверить SSH или пути |
| Ошибка, код 1 | Исправить конфиг/локальную среду по сообщению |
| Прерывание, код 130 | Сеанс остановлен пользователем; уже собранное сохранено, SSH закрывается |

Если SSH закрыт, сборщик сохранит результаты ENET. QNX SDK и Docker не открывают SSH на магнитоле. Метод доступа выбираем по фактической firmware; нужный клиент доступа готовим заранее для работы без интернета. Подбор паролей и разблокировка в сборщик не включены.

### Где искать результат

Каждый запуск создаёт отдельную приватную папку в `.build/nbt-qnx/sessions/`, дата — по Москве. Локальные артефакты остаются вне Git.

| Файл/каталог | Содержание |
|---|---|
| `config-used.json` | Параметры именно этого сеанса после применения значений по умолчанию |
| `summary.json` | Итог, IP шлюза/HU, версия ОС, firmware и её источник, экран, ошибки и список файлов с хешами |
| `ifconfig.txt`, `gateway-route.txt`, `head-route.txt` | Сеть и проверенные маршруты |
| `discovery.txt` | Необработанные ответы обнаружения, если discovery выполнялся |
| `identify.txt`, `identify.json` | Ответы идентификации, включая отрицательные ответы и ошибки |
| `uname.txt`, `nbt-version.txt`, `display.txt`, `cpu-info.txt` | Данные HU при работающем SSH |
| `*.stderr.txt` | Ошибки команд отдельно от данных; исключение — первый интерактивный SSH-диалог, он остаётся в Терминале |
| `frameworks/libAppFramework.A.so`, `frameworks/libCoreFramework.A.so` | Две прочитанные HMI-библиотеки |
| `runtime/…` | Runtime с сохранёнными исходными путями: например, `runtime/usr/lib/libc.so.3` |
| `runtime-paths.txt`, `search-…txt` | Найденные пути и поиск отсутствующей HMI-библиотеки |
| `SHA256SUMS.txt` | Хеши всех успешно скопированных бинарников |

Если один runtime найден по нескольким путям, сохраняются все варианты с их происхождением. Сборщик не угадывает, какой из них использует загрузчик. При ошибке SSH/копирования или неверном ELF итоговый бинарник не публикуется. Ввод firmware из конфига имеет статус `reported`; обнаруженный по SSH код — `confirmed` в границах данного адреса, а расхождение явно попадает в отчёт.

Фото экрана положить в указанную папку как `firmware-menu.jpg`. После сбора изучаем `summary.json` и переносим подтверждённые факты/хеши в журнал ниже; библиотеки и сырые логи остаются локально.

### Следующий этап

`collect` выполняет сбор данных и не загружает/не запускает наши приложения на HU. После анализа ОС, CPU, loader/libc и библиотек HMI готовим отдельный шаг запуска console Hello World. Затем — собственный HMI-счётчик под фактический экран и проверенный BMW ABI. Сейчас эти проверки на автомобиле остаются `planned`.

Исходники: [сборщик](../../../tools/nbt_session.py), [конфиг](../../../config/nbt/session.example.json), [тесты имитаторов](../../../tools/tests/test_nbt_session.py). Локально прошли 17 тестов, `check` и `collect --dry-run`. Сеть автомобиля и его файлы в этих проверках не использовались.
