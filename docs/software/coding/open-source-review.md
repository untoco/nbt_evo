# evocode и открытые проекты для кодирования BMW

> Версия: 2026-11-17. Область: BMW F21 N13B16, настройки автомобиля на macOS/ENET и установленная NBT Evo. Исследование и офлайн-проверки; в автомобиль ничего не отправлялось. Единый [план задачи](plan.md) содержит ближайший шаг и журнал продолжений.

[Раздел ПО автомобиля](../README.md)

## Вывод

`confirmed` по исходникам: evocode содержит предметную реализацию NBT Evo — HSFZ, SREC/NCD, подпись, L3 и последовательность записи. Это полезная основа отдельного HU-клиента, но не универсальное кодирование настроек всей машины. Готовность записи в наш F21 — `unknown`: нет нашего NCD и точного CAFD-файла, штатные preflight-проверки недостаточны. На первом этапе используем проект для офлайн-изучения и подготовки чтения, без `--commit`.

`planned`, решение для процесса: BimmerCode macOS — кандидат для обычных настроек KOMBI/FEM; evocode — исследовательский путь HU; OpenCAFDMap — источник описаний и сравнения; klartext/EdiabasLib — диагностические компоненты; IDEmu — дополнительная проверка HU офлайн. Поддержка конкретных блоков/сборок нашей машины каждым из этих инструментов пока `unknown`.

## Что проверено в evocode

Источник: [FreZZZeR/evocode](https://github.com/FreZZZeR/evocode), commit [`913d5733e04019d4134f825b8fa0cc65782d02f7`](https://github.com/FreZZZeR/evocode/commit/913d5733e04019d4134f825b8fa0cc65782d02f7), дата проверки 2026-11-16. Исходники загружены в игнорируемый `.build/research/evocode`; сторонний код в основной репозиторий не копировался. `pyproject.toml` задаёт 0.3.0 и Python ≥3.9; README ещё говорит 0.2.x. Лицензия Apache-2.0, дополнительные зависимости — crypto/SSH/test (`confirmed` по файлам).

### Поддерживаемая область

- `confirmed` по [cli.py](https://github.com/FreZZZeR/evocode/blob/913d5733e04019d4134f825b8fa0cc65782d02f7/evocode/cli.py): identify/read/decode/verify/sign/write; запись по умолчанию dry-run, до сетевого соединения проверяется локальная подпись, при commit сверяется VIN. `_write_order` ставит datagroup подписи последней.
- `confirmed` по [coding.py](https://github.com/FreZZZeR/evocode/blob/913d5733e04019d4134f825b8fa0cc65782d02f7/evocode/coding.py): единственная схема `nbtevo`, MD5 по `0x3000…0x300F`, подпись в `0x3010`; RSA/word swap реализованы. Наличие параметра `--target` не добавляет алгоритмы FEM/KOMBI.
- `confirmed` по [протоколу](https://github.com/FreZZZeR/evocode/blob/913d5733e04019d4134f825b8fa0cc65782d02f7/docs/protocol.md) и коду: coding использует UDS-сессии, SecurityAccess, запись datagroup, проверку подписи, CPS и reset. SSH в этом пути не участвует. Это соответствует доступному у нас классу транспорта, но не доказывает успешную запись.
- `reported` автором: воспроизведение подписи реального NCD byte-for-byte на CAFD 006.031.014; это свидетельство о подписи/данных другой HU, не наш результат. FSC owner-CA и OPT_DEBUG обозначены как ещё не проверенные на живом блоке. Данные функции не нужны для обычного изменения настроек.

### Замечания, важные до автомобильной записи

1. **Неполный backup может выглядеть успешным.** `cmd_read` ловит любой `UdsError` и считает datagroup отсутствующей. На офлайн-имитаторе отказ всех чтений с NRC `0x33` создал файл с нулём datagroup и возвратом 0; сообщение всё равно называет его пригодным для возврата. Это `measured` на mock, не автомобильная ошибка. Нужны протоколирование каждого отказа и проверка ожидаемого состава/длины/подписи; отказ доступа не равен отсутствию данных.
2. **Нет строгого сопоставления ответа запросу.** В [hsfz.py](https://github.com/FreZZZeR/evocode/blob/913d5733e04019d4134f825b8fa0cc65782d02f7/evocode/hsfz.py) `request` снимает два адресных байта без сверки source/target; `Uds.read_did` проверяет SID, но не echoed DID. Mock-ответ `62 F1 90 41 42` принят для запроса F101 (`measured`). До доверия чтению нужны проверки адресов, DID/subfunction/routine и длины.
3. **Версия каталога не защищает автоматически.** [catalog.load](https://github.com/FreZZZeR/evocode/blob/913d5733e04019d4134f825b8fa0cc65782d02f7/evocode/catalog.py) возвращает параметры без CAFD/version metadata. `cmd_decode` не сравнивает каталог с SVK. До sign/write требуется внешняя проверка точного варианта. Старые смещения нельзя брать из README как готовую команду для нашей HU.
4. **VIN — только одна проверка адресата.** `cmd_write` не читает SVK для сравнения с NCD/key/catalog, не проверяет полноту копии и не требует baseline hash. Валидная локальная подпись не доказывает правильный ECU/вариант. Он записывает все присутствующие datagroup из входного NCD, а не только diff, несмотря на формулировку «changed» в описании протокола (`confirmed` по коду).
5. **Readback кодировок оставлен оператору.** В write читается CPS, но полное повторное чтение coding data не автоматизировано; сравнение CPS тоже выводится без проверки равенства. Нужны отдельный readback, сравнение данных и тест функции после перезапуска. Пустой status CheckCodingSignature сейчас не отвергается (`confirmed` по ветвлению кода); его формат необходимо сверить с нашим блоком до доверия результату.
6. **Ожидание не ограничено общим сроком.** ResponsePending продлевает deadline каждый раз; receive читает объявленную длину без верхнего лимита. Нужны общий дедлайн, границы frame и фиксация ошибок. Это наблюдение статического ревью, не воспроизведённый зависший автомобильный сеанс.

Воспроизводимый [офлайн-probe](../../sources/coding/2026-11-16_evocode_offline_probe.py) и [его результат](../../../logs/coding/2026-11-16_evocode_offline_probe.json) сохранены. Он использует fake transport и не открывает сокеты.

### Что реально запущено

`measured`, macOS/Python 3.15, 2026-11-16:

```sh
python3 .build/research/evocode/tests/test_coding.py
python3 .build/research/evocode/tests/test_anchors.py
python3 docs/sources/coding/2026-11-16_evocode_offline_probe.py .build/research/evocode
```

- core self-run: восемь офлайн-проверок выполнены успешно; девятая, real-signature, фактически пропущена из-за отсутствия реального NCD/key, хотя runner печатает «ALL 9 TESTS PASSED»;
- anchors: четыре синтетических проверки выполнены успешно;
- полный `python3 -m pytest -q .build/research/evocode/tests` не запущен: `No module named pytest`; пакеты для этого не устанавливались;
- наше NCD, реальные подписи/ключи, чтение/запись машины и запуск IDEmu не проверены.

Успешные синтетические тесты подтверждают только проверенные офлайн-свойства. Они не снимают замечания выше и не доказывают работу кодирования F21.

## Похожие и дополняющие проекты

Дата просмотра всех ссылок: 2026-11-16. Для сравнительной таблицы изучены README/документация авторов, если не указано иное; программы не запускались. Возможности в этих строках — `reported`, практическая применимость на нашем F21 — `unknown`. Это целевой shortlist, не полный обзор всех репозиториев BMW.

| Проект | Что даёт | Ограничения и применение |
|---|---|---|
| [OpenCAFDMap](https://github.com/shamair28/OpenCAFDMap) | Имена и определения CAFD, сравнение NCD, интеграция E-Sys; BimmerCode Backup Editor | Заявленный workflow Windows + E-Sys/PSdZData, не самостоятельный ENET writer на Mac. Полезен для исследования карт и семантики; лицензию отдельных data/code проверять отдельно (MIT/CC0 и иные notices) |
| [klartext](https://github.com/HadiCherkaoui/klartext) | Rust HSFZ/UDS, DTC/идентификация, ISTA/SGBD, MCP-диагностика | Автор прямо исключает general FDL/CAFD editor и replay-coding. Кандидат диагностики до/после изменения, не замена evocode для записи. AGPL-3.0-only; репозиторий обозначен read-only mirror |
| [EdiabasLib / Deep OBD](https://github.com/uholeschak/ediabaslib) | .NET-интерпретатор PRG/GRP, диагностические задания, ENET | Нужны подходящие SGBD/job и среда. Сам по себе не готовый FDL-клиент для F21/macOS. GPL-3.0; отдельные задания могут менять состояние |
| [IDEmu](https://github.com/herrbimmer/IDEmu) | Эмулятор HU для macOS, реальное ПО из собственных firmware packages, интерфейс и coding editor | Кандидат офлайн-проверок HMI. Не кодирует всю физическую машину. PolyForm Noncommercial, QEMU-компоненты с отдельной лицензией |
| [BIT-Tuning](https://github.com/krisna24/BIT-Tuning) | Python GUI, заявлены ENET/coding/diagnostics | [Предыдущее статическое ревью](plan.md#проверка-открытого-кандидата-bit-tuning) выявило общие DID/offset, несовпадающий адрес KOMBI и неполный диапазон чтения. На этой машине не проверен; не выбирать writer по рекламному списку. MIT по метаданным GitHub |

Отдельный существенный предел OpenCAFDMap: [Backup Editor](https://github.com/shamair28/OpenCAFDMap/blob/main/docs/BC_EDITOR.md) поддерживает **iOS .cod**, Android пока нет; поддержку desktop-формата из этого не выводим. Редактор сохраняет старый блок подписи, а автор прямо оставляет неизвестным, переподпишет ли его BimmerCode при restore. Поэтому редактирование backup не принимаем как готовый путь записи HU; сначала нужны проверка формата/подписи и конкретной версии клиента.

По [документации evocode об IDEmu](https://github.com/FreZZZeR/evocode/blob/913d5733e04019d4134f825b8fa0cc65782d02f7/docs/testing.md) эмулятор не предоставляет HSFZ endpoint для проверки диагностического write. Даже удачный boot изменённого образа не доказывает успешный автомобильный транспорт или принятие coding/FSC. Формулировку автора о boot-safe не распространяем на все риски реальной HU.

## Как использовать находки в нашем процессе

1. `planned`: получить инвентаризацию реальных настроек KOMBI/FEM/HU и исходные копии без изменения значений; не смешивать стандартные настройки с активациями/прошивкой.
2. `planned`: для evocode закрыть проверку полноты backup, корреляцию ответов и выбор точной версии; получить CAFD `00001EF6 / 006.052.007` из доступного владельцу источника. Не сохранять PSdZData/ключи в Git.
3. `planned`: подтвердить две одинаковые копии NCD, SREC round-trip, соответствие ключа BTLD и подпись исходного NCD. До этого sign/write — только синтетические данные.
4. `planned`: подготовить одну требуемую функцию, diff, питание LTO, readback и возврат исходной копии по [процессу](plan.md#процесс-одной-сессии). Запись выполняется в рамках конкретно выбранной работы.

Корневой доступ, OPT_DEBUG/SWDL, замена NBTCarHU и FSC owner-CA остаются отдельными работами в [плане NBT Evo](../nbt-evo/plan.md). Их существование в evocode не означает необходимости для изменения обычных параметров и не расширяет авторизацию текущей задачи.
