# Кодирование F21 через ENET с macOS без E-Sys

> Версия: 2026-11-17. Область: принадлежащий владельцу BMW F21 N13B16; процесс кодирования настроек через macOS/ENET. Статус процесса: `planned`, автомобильная запись по нему не выполнялась. Этот файл — единый рабочий план задачи и журнал её продолжений.

## Вывод и границы готовности

- `measured`: ранее на этой машине работали ENET discovery, TCP 6801 и UDS-чтения через шлюз. Для HU и KOMBI прочитан SVK, включая идентификаторы CAFD. Это подтверждает транспорт и идентификацию, но не чтение значений кодирования и не запись.
- `confirmed` по официальному сайту: BimmerCode распространяет desktop-сборки macOS 12+ для Intel и Apple Silicon. Производитель перечисляет F20/F21, ENET cable + Ethernet adapter и функции для FEM, KOMBI и HU_NBT_EVO. Совместимость конкретного блока и desktop-сеанса на нашем F21 остаётся `unknown` до проверки.
- `confirmed` локально: Mac — Darwin arm64, macOS 27.0.1; Python 3 доступен. В просмотренном /Applications BimmerCode не установлен. В проверенных `.build/`, `config/`, `tools/` вне QNX toolchain не обнаружены файлы CAFD/NCD/PSdZData. Это ограниченная инвентаризация, а не поиск по всему диску.
- `planned`: управляемое агентом кодирование через готовый клиент macOS — практический кандидат без E-Sys и Windows. Покупка лицензии, установка клиента, чтение им машины и запись в этой задаче не выполнялись.
- `unknown`: способность нашего собственного Python-клиента читать и записывать кодировки. Сейчас он реализует discovery/идентификацию, но не полноценный CAFD/NCD workflow. Разработать ограниченный клиент технически представляется возможным; сроки и поддержка всех ECU не установлены.

## Два разных пути

### 1. Готовый BimmerCode для macOS

`reported` производителем: поддерживаются обычные настройки F21, например цифровая скорость при совместимой KOMBI, память Auto Start Stop в FEM и настройки интерфейса HU. Реальная доступность зависит от установленных блоков и их ПО.

Особенность нашей машины: NBT Evo доустановлен вместо ENTRY_BASIS, с расширенной приборкой и MOST (`reported` владельцем). CarPlay работает, метод его активации неизвестен. Официальная инструкция BimmerCode предупреждает, что ретрофитный iDrive может быть недоступен, а сторонняя активация CarPlay/навигации может препятствовать кодированию HU. Не удалять существующую активацию ради проверки без отдельного решения о её восстановлении.

`reported`: для fullscreen CarPlay производитель указывает NBTevo_X/Y. У нашей HU в меню X20511I (`reported` владельцем), что делает функцию кандидатом по версии; текущий fullscreen, доступ клиента и совместимость активации не проверены.

Desktop-лицензия отдельная, привязана к машине по FAQ производителя; наличие мобильной покупки не считать наличием desktop-лицензии.

### 2. Собственный клиент на Python

HSFZ/UDS не привязаны к Windows. Наличие готового транспорта на Mac снимает лишь нижний уровень задачи. Для изменения конкретного параметра нужны:

1. Идентификация целевого ECU и точного варианта CAFD; чтение текущих coding data по проверенной процедуре.
2. Точное описание параметра для этой версии, формат данных и способ сборки изменённого coding payload. Обычно источником описаний служит соответствующий CAFD из PSdZData; альтернативой может быть отдельно проверенная карта конкретного варианта. Установка E-Sys сама по себе для транспорта не нужна.
3. Проверенная последовательность диагностических сессий, доступа, передачи и завершения кодирования именно этого ECU. Не предполагать, что любой блок принимает простой UDS WriteDataByIdentifier.
4. Сохранённые исходные данные и проверенный план восстановления, минимальный diff, повторное чтение после записи и функциональная проверка. Копия кодировок сама по себе не является способом восстановления повреждённой прошивки.

FDL-подобное изменение параметров, VO-кодирование по комплектации и flash ПО — отдельные задачи. Последние две не считать автоматически реализованными после первой. VO-кодирование ретрофитных блоков без сохранения текущих изменений может заменить индивидуальные настройки; FA нашей машины ещё неизвестен.

## Проверка открытого кандидата BIT-Tuning

`confirmed` по статическому чтению исходников 2026-11-16; на машине не запускался:

- `bmw/coding.py`, Git blob `daac3ea9a87f086fbe448f583f70b5b02559f85d`: фиксированные DID/byte/bit, общие определения для NBT/NBT Evo без выбора по точному CAFD; KOMBI указан `0x70`, тогда как наша приборка ответила на `0x60`.
- `read_coding` перебирает `0x3000..0x301F`, но в таблице есть параметр `0x3056`, который этот проход не читает.
- Запись изменённого блока выполняется через `write_did`; в просмотренном пути нет повторного чтения для подтверждения результата. Наличие такого метода не доказывает соответствие процедуре кодирования нашего ECU.
- `core/security.py`, Git blob `2cfb5bada028ef999c3959126efeaf6d9c3c7641`: общие CRC/XOR-кандидаты и режим перебора, без подтверждения применимости к нашим блокам.

Вывод (`confirmed` как результат ревью): это не проверенная реализация кодирования нашего F21. Использовать рекламное описание проекта как доказательство готовности нельзя. Не переносить его адреса, смещения и security access в рабочую запись без независимой проверки.

## Связь с задачей SSH

Кодирование ECU через диагностический шлюз и SSH в ОС NBT Evo — разные пути. Для диагностического coding workflow сам по себе SSH не является обязательным. Наши успешные UDS-чтения при недоступном TCP 22 подтверждают эту разницу; они не гарантируют будущую запись. Не объявлять отсутствие SSH либо неизвестную Ethernet-проводку HU универсальным запретом на кодирование FEM/KOMBI. [Отдельный план HU](../nbt-evo/plan.md).

## Процесс одной сессии

Все пункты ниже — `planned`, правила нашего процесса, а не отчёт о выполненном кодировании. Проходим этапы последовательно; при незакрытом условии продолжаем подготовку без записи. Авторизацию уже выбранной работы не запрашиваем повторно на каждый пакет.

### 1. Реестр настроек

Сначала проверяем доступные штатные меню: если настройка меняется там, фиксируем её без кодирования ECU. Для оставшихся функций собираем реестр; наличие функции в каталоге производителя — `reported`, на нашем автомобиле — `unknown` до чтения.

| Кандидат | Предполагаемый блок | Что выяснить до выбора |
|---|---|---|
| Цифровая скорость, состав борткомпьютера | KOMBI | Фактический вариант, поддержка и текущее значение |
| Память Auto Start Stop | FEM | Идентификаторы, доступность и пожелание владельца |
| Складывание зеркал при запирании | FEM | Наличие электроскладывания и зависимых настроек |
| Настройки комфорта и запирания | FEM / HU, по конкретной функции | Что уже доступно в меню; нужные блоки и оборудование |
| Интерфейс iDrive / CarPlay | HU_NBT_EVO | Точный CAFD, состояние ретрофита и способ активации |

Это очередь обследования, а не пакет к применению. Список поддержанных функций сверяется с [каталогом F20/F21](https://bimmercode.app/vehicles/f20/). DME/EGS с MHD/xHP, DSC/ACSM, изменение типа аккумулятора и VO-кодирование ретрофита не включаем в первый сеанс настроек; для них нужна отдельная конкретная задача в этом же плане.

### 2. Подготовка и выбор клиента

1. Записать дату/время с часовым поясом, VIN, версию клиента, адаптер, интерфейс Mac, локальный IP и найденный адрес шлюза. Исторические IP не использовать без проверки маршрута и VIN. `--host` evocode — диагностический HSFZ endpoint, им может быть шлюз; доступность прямого IP HU и SSH — отдельные проверки.
2. Автомобиль стоит, АКП в P, стояночный тормоз включён. Для BimmerCode: двигатель выключен, зажигание включено, потребители отключены. Закрыть остальные диагностические клиенты. DataTrack и другие сторонние CAN-устройства учесть по инструкции клиента; отключать по понятной процедуре, без случайного изменения проводки.
3. Подтвердить питание: модель источника поддержки, совместимость с VISSO LTO1240AT, подключение и допустимый диапазон по документации аккумулятора/источника/клиента; записать напряжение до/во время/после. Маркировка батареи 10–16 V не задаёт напряжение поддержки. Пока эти условия `unknown`, запись не начинать. Не выбирать AGM/recondition-режим по коду «55 Ah, не AGM».
4. Предпочтительный кандидат для обычных настроек — BimmerCode macOS; реальная поддержка наших блоков и адаптера проверяется чтением. ENET-совместимость нашего скрипта не доказывает поддержку modBMW конкретным клиентом. При проблеме проверить поддержанный проводной ENET. Покупку лицензии не считать выполненной.
5. evocode рассматриваем отдельно для HU, после офлайн-проверок. Наличие `--target` не делает его клиентом FEM/KOMBI. Root/FSC/flash не являются этапами обычного кодирования настроек.

Основание пунктов подготовки — [официальная инструкция](https://bimmercode.app/manual/), проверена 2026-11-16 (`reported`); условия питания LTO — локальное требование процесса, конкретные численные пределы пока `unknown`.

### 3. Чтение и исходная копия

- Подтвердить VIN и целевой ECU; сохранить HWEL/BTLD/SWFL/CAFD с версиями и I-Step, если клиент его читает. FA/VO и SVT Actual сохранить при доступности, особенно перед будущими изменениями ретрофита. Недоступные данные отметить `unknown`.
- Сохранить исходные ошибки до их очистки, текущее поведение и скриншоты параметров. Фиксировать, какие блоки не читались.
- Считать текущие кодировки целевого блока. В BimmerCode Desktop: Settings → Manage files → `backups`; скопировать резервную копию вне каталога приложения, проверить размер, SHA-256 и соответствие VIN/ECU/дате. Способ её выбора для восстановления проверить в текущей версии интерфейса, без запуска записи.
- Для собственного клиента получить два независимых чтения, сравнить состав/длины datagroup и значения. Любой отказ чтения сохранить с DID/NRC; пустой либо неполный файл не считать резервной копией. Проверить SREC round-trip, подпись и точный CAFD перед редактированием.
- Исходная копия — **текущая рабочая конфигурация ретрофита**, а не автоматически заводская. Не заменять её VO-default или самым старым backup другой сессии.

### 4. Подготовка конкретного изменения

Заполнить [карточку](../../../logs/coding/change-template.md): одна функция, один блок либо явно описанный набор зависимых блоков. Зафиксировать исходное/новое значение, источник назначения параметра, версию CAFD и проверяемое поведение. Для собственного клиента показать diff данных, включая ожидаемое изменение подписи; для GUI — список настроек и скриншоты до/после подготовки. Если клиент не предоставляет сырой diff, отметить ограничение.

Для HU сначала подтвердить сохранение CarPlay и индивидуальных кодировок ретрофита. Не снимать существующую активацию только ради допуска клиента. Сохранить исходный payload и CPS, определить процедуру возврата выбранным клиентом. Перед записью должны быть известны условия восстановления связи и исполнитель восстановления при недоступности ECU. NCD не восстанавливает повреждённую прошивку.

### 5. Запись и проверка

Выполнить только выбранное владельцем изменение при выполненных условиях выше. Сохранить точное время, результаты клиента и существенные запросы/ответы/ошибки. Не повторять автоматически запись или SecurityAccess после отказа. Дождаться штатного завершения и предписанного перезапуска; не отключать питание/адаптер во время операции.

После восстановления связи повторно считать параметры. Для NCD сравнивать декодированные данные, отдельно подпись и служебные поля; сравнение только текста файлов недостаточно. В GUI повторно открыть блок и прочитать значение. Затем проверить функцию на машине и отсутствие регрессий: KOMBI, iDrive, звук, CarPlay и связанные настройки по области изменения. Убедиться, что значение сохраняется после предусмотренного циклом клиента выключения/включения. Ошибки до/после сравнить; очистку ошибок выполнять только как отдельно выбранную операцию с сохранённым исходным отчётом.

Статусы результата: запись подтверждена ответом клиента — `reported`; значение повторно прочитано — `measured`; работа функции подтверждена проверкой — `confirmed` с указанием проверяющего/свидетельства. Без функционального теста не писать «работает».

### 6. Откат и завершение

При несоответствии значения, новых устойчивых ошибках либо регрессии функции остановить дальнейшие изменения, сохранить доступные логи. Если ECU доступен и питание стабильно, восстановить **копию непосредственно перед изменением** штатным workflow клиента, затем повторить чтение и функциональный тест. При потере диагностического доступа сначала проверить питание, маршрут и VIN при восстановлении связи; не переходить автоматически к flash/root/сбросу в заводские настройки.

Сессия завершена, когда исходная копия сохранена, результат либо откат прочитан повторно, поведение проверено, ошибки сопоставлены и карточка заполнена. Для нового подтверждённого состояния обновить спецификацию и раздел 13; раздел 11 — при изменении состава компонентов. Затем проверить файлы, коммитить и отправить в origin/main.

## Артефакты сессии

- `logs/coding/YYYY-MM-DD_HHMM_<ecu>_<function>/`: заполненная карточка, before/after NCD либо backup клиента, отчёт ошибок, diff и SHA-256, журналы. Время в карточке — с UTC offset.
- `media/coding/`: фото/скриншоты результата, связанные из карточки.
- `.build/coding-private/`: ключи и локальные проприетарные входные материалы; каталог исключён из Git общим правилом `.build/`. В журнале хранить только назначение/путь, не содержимое ключей.
- [Ревью открытых проектов](open-source-review.md) — исследование инструментов; продолжения задачи фиксировать в настоящем плане.
